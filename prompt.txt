Build a production-grade backend for a medicine delivery app (rural India users). Stack: Node.js, Express, MongoDB (Mongoose), Socket.io, JWT. Use clean modular structure (routes / controllers / services / models / middleware / sockets), async/await, centralized error handling, and env-based config.

SCOPE (customer side only): accounts, carts, order history, active orders. Plus the order pipeline to the admin panel.

1. AUTH: MOBILE NUMBER + OTP
- POST /auth/send-otp { phone } and POST /auth/verify-otp { phone, otp }.
- Normalize phone to E.164 (+91). Validate strictly.
- OTP: 6 digits, hashed (bcrypt or HMAC) before storing, TTL 5 min (Mongo TTL index), max 5 verify attempts, 30s resend cooldown, rate limit per phone and per IP.
- SMS behind a provider interface (stub it for dev; log OTP to console in development only) so MSG91/Twilio/Fast2SMS can be plugged in.
- Login and signup are the same flow. On successful verify:
  - If no user exists with this phone, create it with isNewUser = true.
  - If the user exists, update lastLoginAt.
  - Return { accessToken (15 min), refreshToken (30 days, rotated, stored hashed), user, isNewUser, message }.
- Messages in the response:
  - New user: "Welcome to <AppName>! Your medicines, delivered to your doorstep." with a short description.
  - Existing user: "We miss you!" plus a short description (e.g. "Your cart and past orders are right where you left them.").
- Set a hasSeenWelcome flag so the welcome shows only once. Existing users get the "miss you" message on each fresh login.
- POST /auth/refresh, POST /auth/logout (revoke refresh token).
- Auth middleware verifies JWT and attaches req.user. Use the same JWT to authenticate Socket.io connections.

2. CUSTOMER ACCOUNT
- User: phone (unique, indexed), name, saved addresses (village, landmark, pincode, optional geo point), defaultAddressId, createdAt, lastLoginAt, isNewUser, hasSeenWelcome.
- GET/PATCH /me, CRUD for /me/addresses.

3. CART
- One cart per user, stored in MongoDB, linked to the user's phone/userId.
- A cart item is either a catalog medicine (productId, qty, price snapshot) or an uploaded item (prescription photo / medicine strip photo, with image URL and note).
- Endpoints: GET /cart, PUT /cart/items (add/update/remove), DELETE /cart. All writes idempotent and atomic ($set / $inc / arrayFilters, no read-modify-write races).
- Recompute totals server-side. Never trust client prices.
- Cart persists across devices and is restored automatically after login.

4. ORDERS
- Order types: catalog order, prescription-photo order, strip-photo order, or mixed.
- POST /orders converts the cart to an order inside a Mongo transaction: snapshot items, prices, address, and customer phone, generate a human-friendly orderNumber, clear the cart. Support an Idempotency-Key header so double taps never create duplicate orders.
- Status flow: PLACED -> CONFIRMED (admin reviewed / prescription verified) -> PACKED -> OUT_FOR_DELIVERY -> DELIVERED, plus CANCELLED / REJECTED. Allow only valid transitions. Keep a statusHistory array with timestamps and actor.
- Prescription / strip orders may start with unpriced items: admin sets final prices after review, and the order moves to AWAITING_CUSTOMER_CONFIRMATION when the total changes. Customer accepts or cancels.
- Customer endpoints:
  - GET /orders/active (statuses not DELIVERED / CANCELLED / REJECTED)
  - GET /orders/history (paginated, cursor-based, newest first)
  - GET /orders/:id
  - POST /orders/:id/cancel (only before PACKED)
- Indexes: { userId, createdAt: -1 }, { userId, status }, { status, createdAt } for the admin queue.

5. IMAGE UPLOADS
- POST /uploads (multipart): accept jpg/png/webp only, size limit, magic-byte check, compress/resize server-side (sharp). Store through a storage interface (local disk for dev, S3/Cloudinary-compatible for prod). Return the URL for use in cart/order items.

6. SOCKET.IO (LIVE UPDATES, NO POLLING)
- Authenticate on handshake with the JWT.
- Rooms: user:<userId> for customers, admins for the admin panel, order:<orderId> for tracking.
- Events to customer: order:created, order:status_changed, order:price_updated, order:eta_updated.
- Events to admin room: order:new (full order payload), order:updated, order:cancelled_by_customer.
- Emit from the service layer after the DB commit succeeds, never before.
- On reconnect, the client can request missed state via GET /orders/active, so sockets are an optimization and REST stays the source of truth.
- Include a Redis adapter hook (optional via env) for horizontal scaling.

7. ADMIN PANEL HANDOFF
- Admin-only endpoints (role-based middleware): GET /admin/orders (filter by status, date, search by phone/orderNumber, paginated), GET /admin/orders/:id, PATCH /admin/orders/:id/status, PATCH /admin/orders/:id/pricing.
- New orders show up in the admin panel instantly via the socket event, with a lean payload (id, orderNumber, customer name/phone, item count, type, total, createdAt) and full details fetched on open.

8. QUALITY / PERFORMANCE
- Input validation on every route (zod or Joi), helmet, CORS allowlist, rate limiting, compression, request logging (pino), health check endpoint.
- Use .lean() for read queries, project only the needed fields, and keep all list endpoints paginated.
- Consistent response format: { success, data, error: { code, message } }.
- Graceful shutdown, Mongo connection pooling, and env validation at startup.
- Provide: folder structure, all models with indexes, a .env.example, a seed script (sample medicines + an admin user), and a Postman/Thunder collection or an OpenAPI file.

Deliver the complete working code, file by file, with brief comments only where logic is non-obvious.
